## 클래스

| index | 이름 | 무엇 |
|---|---|---|
| 0 | `amr` | 상대 TurtleBot4 |
| 1 | `worker_b` | 주황·가로줄 상의, 전고 285 mm |
| 2 | `worker_a` | 파랑·세로줄 상의, 전고 265 mm |

**인덱스 순서가 이름 순이 아니다** — 데이터셋 `data.yaml` 이 알파벳순이라 `amr` 이 0 번이다.
클래스를 코드에서 다룰 때는 **이름으로** 거른다(`best_box()` 가 그렇게 돼 있다). 인덱스로 매핑하면 셋이 통째로 뒤바뀌는데,
검출은 정상으로 보이고 페어링만 전부 틀리는 형태로 나타난다.

`outfit_class` 는 **복장**을 가리킨다 (계약 2절, `WorkerDescriptor.msg`). 개체 이름이 아니다 —
AC-10 은 상의를 벨크로로 바꿔 달고 판정이 **옷을 따라가는지 몸통을 따라가는지** 보는 시험이므로,
클래스 이름이 복장을 가리켜야 결과를 해석할 수 있다.

### `amr` 클래스 (계획에 없던 추가, 9/7)

**회피용이 아니다.** 상대 로봇을 "작업자 아님" 으로 명시 분류해 `target/*` 후보에서 빼기 위한 **네거티브 클래스**이고,
AC-04(ID Swap 0건)에 기여한다. 회피는 `safety_watchdog` + Nav2 costmap(LiDAR·범퍼)만으로 성립한다는 안전 계층
원칙(`AGENTS.md`)이 그대로 유효하고, 웹캠·카메라 검출을 주행 회피에 연결하지 않는다 (costmap 주입은 Phase 2).
`mro_interfaces`·`docs/interfaces.md` 변경 없음.

## 학습 (I-003)

YOLO 패밀리 스윕 18건, RTX 4070, 9 h 19 m. 챔피언은 `yolo26s` @ 800 이었으나 **배포는 640** —
800 대비 mAP50-95 손실이 0.09 %p 인데 추론이 1.6 배 빠르다 (보고서 §7 비용·효익).

| | |
|---|---|
| run | `p2_yolo26s_img640_sgd_lr0.01_strong_cos` |
| 레시피 | `yolo26s.pt` · imgsz 640 · batch 16 · SGD lr0 0.01 · cos_lr · strong aug · 130 epochs · seed 42 |
| val | mAP50 0.9948 · mAP50-95 0.8161 · P 0.9931 · R 0.9948 |
| test (미사용 셋) | mAP50 0.9950 · mAP50-95 0.8026 — 과적합 징후 없음 |
| 혼동행렬 | **`amr` ↔ 작업자 오분류 0건.** 대각선 밖이 비어 있다 |

재현:

```bash
yolo train model=yolo26s.pt data=<dataset>/data.yaml \
    epochs=130 imgsz=640 batch=16 optimizer=SGD lr0=0.01 lrf=0.01 cos_lr=True seed=42
```

학습 라벨은 `steve`(=worker_a) · `ari`(=worker_b) 였고, 계약 이름으로 바꿔 저장했다.
가중치는 건드리지 않는다 — 클래스 이름은 체크포인트 안의 `model.names` dict 일 뿐이고,
신경망은 채널 인덱스만 출력한다 (교체 전후 파라미터 SHA-256 동일 확인).

### confidence

conf 스윕(val)에서 F1 최적은 0.4 지만 **0.5~0.6 을 쓴다.** F1 은 오탐과 미탐의 비용이 같다고 보는데
우리는 대칭이 아니다 — 미탐은 Lost 후 재탐지 절차가 설계돼 있고 K-04 로 측정되지만, **오탐은 오추종이고
AC-04 는 0건이 절대 기준**이다. 0.4 → 0.6 에서 오탐 6 → 2, 재현율은 1 %p 만 떨어진다.
값은 `config/perception.yaml` 의 `detect_conf` 가 단일 출처다.

## 추론 속도 (9/7 실측)

**결론 — 모델을 바꾸지 않는다.** 배포본이 10 Hz 예산의 20 % 만 쓴다.

측정 조건: RTX 3060 Laptop **AC 전원** · 2PM valid 실측 이미지 · 웜업 15 버림 · 400 회 · `tools/bench_yolo.py`
이 노트북이 팀 PC 중 **최저 사양**이므로 아래는 보수적 하한이다. 배포 PC 4대 모두 GPU 가 있다.

| 호출 | 쓰는 노드 | min | median | p95 | max | 예산 100 ms 대비 |
|---|---|---|---|---|---|---|
| `predict` | `amr_detection` | 5.5 | **7.3** | 8.4 | 43.9 | 여유 56.1 ms |
| `track` | `webcam_register`·`webcam_hint` | 7.1 | **17.7** | 30.3 | **42.7** | 여유 57.3 ms |

**판정은 평균이 아니라 max 로 한다.** 10 Hz 타이머는 한 프레임만 100 ms 를 넘겨도 그 주기를 흘리고,
`webcam_hint` 는 두 타이머가 겹쳐 돌 수 있다 (I-027).

### 후보 13종 비교 (`track`, AC 전원, GPU)

정확도 차이가 속도 차이를 정당화하지 못한다 — nano 최고(`yolo26n` 0.8040)와 배포본(0.8161)이 **1.2 %p** 다.
우리가 재는 것은 "인형을 놓치는가" 이지 bbox 꼭짓점 정밀도가 아니다.

| 모델 | 파라미터 | mAP50-95 | median | max |
|---|---|---|---|---|
| `yolo26n` @640 | 2.57 M | 0.8040 | 11.1 | 273.0 |
| `yolo11n` @640 | 2.62 M | 0.7978 | 11.5 | 34.2 |
| **`yolo26s` @640 (배포본)** | 10.01 M | **0.8161** | **12.6** | **43.5** |
| `yolo26s` @800 (챔피언) | 10.01 M | 0.8170 | 16.1 | 58.4 |

나머지 9종도 전부 통과(13.6~15.7 ms). 챔피언(800)을 쓰지 않는 이유는 정확도가 0.09 %p 더 좋은 대신
median 이 28 % 느리고, 그 여유를 캡처·ROS·Nav2 에 남겨두는 편이 낫기 때문이다.

### 입력 쪽이 더 큰 지연원이다

추론(7.3 ms)보다 **프레임이 오는 주기(100 ms)** 가 훨씬 크다. 추론을 0 으로 만들어도 그것은 안 없어지므로,
더 작은 모델로 내려도 전체 지연은 거의 줄지 않는다.

아래 2호기 수치는 **교체 전 기체 robot4 에서 잰 값**이다 (9/8 robot8 로 교체). 카메라가 다르므로 참고값으로만 본다.

| 항목 | robot3 | 2호기(구 robot4) |
|---|---|---|
| `oakd/rgb/image_raw/compressed` | 9.30 Hz | 9.45 Hz |
| `oakd/stereo/image_raw/compressedDepth` | 9.15 Hz | 9.45 Hz |
| **동기화 쌍**(`sync_slop_s` 0.1) | **9.15 Hz** | **9.40 Hz** |
| 쌍 성립률 | 98.4 % | 99.5 % |
| stamp 차 median / max | 0.1 / 99.9 ms | 0.1 / 0.1 ms |

RGB 와 depth 가 같은 트리거로 나와 타임스탬프가 0.1 ms 차이다 — `slop` 100 ms 대비 1000 배 여유라
동기화로 버려지는 프레임은 1.6 % / 0.5 % 뿐이다. 다만 **robot3 의 stamp 차 최댓값이 99.9 ms 로 `slop` 에
붙어 있다** — 부하가 늘면 성립률이 떨어질 수 있으니 통합 때 다시 보고, 필요하면 `sync_slop_s` 를 올린다.

작업자 0.3 m/s 기준으로 환산하면 추론 지연은 대상 위치 오차 **5 mm**(최악 13 mm)에 해당한다.
AC-05 허용 오차 200 mm 의 2.7 % 다. **AC-05 를 가르는 것은 지연이 아니라 주행의 추종 제어다** (계약 9.1).

### 재보는 법

```bash
python3 tools/bench_yolo.py --model <worker.pt> --source <2PM valid/images> --imgsz 640 --n 400
```

- **노트북은 반드시 AC 전원.** 배터리에서는 GPU 가 405~982 MHz 로 묶여 같은 모델이 **49 ms → 12.6 ms**,
  4 배 차이가 났다. `cat /sys/class/power_supply/ADP1/online` 이 1 이어야 한다.
- **첫 실행 때 ultralytics 가 `lap`(ByteTrack 의존성)을 자동 설치**한다. 네트워크 없는 곳에서 처음 돌리면
  `track` 이 실패하므로 미리 `pip install lap` 해둔다. 설치가 측정에 끼어들어 최악값을 부풀리기도 한다.
- `results.speed` 는 ByteTrack 시간을 세지 않는다. 타이머 콜백이 겪는 것은 호출 전체이므로 벽시계로 감싼다.

## 한계

- **데이터셋 포화** — 18개 실험이 전부 mAP50 0.99 대다. 이 벤치마크는 모델 간 변별력이 없다는 뜻이지
  실제 아레나의 가림·역광·원거리에서 이만큼 나온다는 뜻이 아니다. 실물 검증은 **TS-U01·U03·U05** 에서 한다.
- **시드 1회** — 상위 5개 격차가 0.51 %p 라 순위가 시드 노이즈보다 크다는 근거가 없다. 배포 선택은
  정확도가 아니라 속도로 갈랐으므로 영향 없다.
- **실부하 미측정** — 아래 속도는 다른 노드가 놀고 있는 상태에서 잰 값이다. 실제로는 같은 PC 에서
  카메라 캡처가 돌고 로봇 제어 PC 는 Nav2·AMCL 까지 함께 돈다. 최종 확인은 통합(9/9)에서 한다.
