# 셔틀 도착 판정 TF 지연 실험

I-037 · 주행 박병후 · 2026-09-08 · 브랜치 `codex/fix-shuttle-tf-arrival`

수정 코드 커밋: `255d832` (`fix: 셔틀 TF 수신 지연과 도착 오판정 수정`).

## 문제 상황과 근거

robot3 미션 T6에서 베이 목표 `(-0.78, 0.138)`에 대해 셔틀은 TF 위치
`(-0.60, -0.20)`, 오차 0.39 m를 기록하고 다음 단계로 진행했다.
다음 전진에서도 같은 위치를 기록했으며 대기공간 오차는 0.55 m였다.

같은 회차의 `bt_navigator_34997_1788845020865.log`를 대조하면 다음과 같다.

| 시각 (ROS 초) | 관측 |
|---|---|
| 1788845470.845546 | controller_server: Reached the goal |
| 1788845470.867305 | bt_navigator: Goal succeeded |
| 1788845470.871230 | 셔틀: TF `(-0.60, -0.20)`, 목표 오차 0.39 m |
| 1788845470.889354 | bt_navigator: 현재 `(-0.65, -0.02)`에서 전진 목표로 시작 |

18 ms 간격의 두 위치가 약 0.187 m 다르다. Nav2의 위치 기준으로는 베이까지
0.205 m여서 현재 `xy_goal_tolerance=0.25`와 부합한다. 셔틀이 만든 전진 목표
`(-0.733324, 0.065801)`까지도 Nav2 위치에서는 0.120 m뿐이다.
**이 로그만으로 실제 로봇의 물리적 위치를 확정할 수 없다.**

해당 회차의 리그는 ID 1·거리 0.9 m를 5 Hz로 주입했다. 따라서 마커 확인은
베이 도착의 독립 실측 증거가 아니다.

## 가설과 실험 계획

| 가설 | 예측 | 판별 실험 |
|---|---|---|
| H1: navigator 대기 중 셔틀 TF 콜백 처리가 밀린다 | 일정 속도 TF 공급 시 버퍼가 과거 위치에 남는다 | 실제 DDS/TF에 20 Hz 이동 공급, 블로킹 1초 + navigator 폴링 2초 전후 비교 |
| H2: Nav2 허용오차가 조기 정차에 기여한다 | 약 20 cm 남아도 성공한다 | 설정·Nav2 로그 대조. 이번 실험에서는 Nav2 설정을 변경하지 않음 |
| H3: 성공 후 검증이 없어 잘못된 관측으로도 전이한다 | 39/55 cm 오차 또는 TF 없음에도 다음 단계로 간다 | Nav2 성공 대역 + 좌표·타임스탬프 결함 주입 회귀 시험 |
| H4: AMCL 보정 또는 stateful 판정이 추가 원인이다 | 최신 TF에서도 순간 오차가 생길 수 있다 | 실물에서 TF·AMCL·Nav2 feedback·물리 위치 대조. 이번에는 미실행 |

진행 순서: 기준 코드 재현 → TF 수신 분리 → 동일 조건 재시험 → 도착/전진 검증
회귀 시험 → 패키지 빌드 → 현장 확인 후 실물 재시험. 사용자 요청으로 실물 실험은 보류했다.

## 수행한 실험과 결과

### E1. 실제 DDS/TF 갱신 지연 재현

기준 코드: 브랜치 시작 커밋 `875024d`의 `shuttle_mission_node.py`.
실험 코드: `ros2_ws/src/mro_navigation/test/test_shuttle_tf_updates.py`.

- 실물 도메인 3과 분리한 **ROS_DOMAIN_ID=201**, localhost, Discovery Server 미사용.
- 실제 rclpy Node·executor·TransformBroadcaster·TF Buffer 사용.
- `map→odom→base_link`를 20 Hz로 발행. 위치는 0.26 m/s로 증가.
- 언독 대기를 1초 블로킹으로, navigator 완료 폴링을 별도 Node의 0.1초 spin으로 재현.
- 실제 Nav2 서버·로봇 주행은 대역이다. 이 실험은 AMCL 정확도나 물리적 정차 오차를 검증하지 않는다.
- 합격: TF 지연 < 0.3초, 합성 위치 오차 < 0.078 m (= 0.26 × 0.3).

| 코드 | TF 지연 | 합성 위치 오차 | 결과 |
|---|---:|---:|---|
| 수정 전, 샌드박스 안 | 2.084 s | 0.542 m | 실패, DDS 소켓 경고 있음 |
| 수정 전, 소켓 제한 제거 | 2.086 s | 0.542 m | 실패, 경고 없음 |
| 수정 후, 소켓 제한 제거 | 0.014 s | 0.004 m | 통과, 경고 없음 |
| 최종 오프라인 스크립트 재검증 | 0.013 s | 0.003 m | 통과, 경고 없음 |

같은 조건에서 TF 수신을 분리하면 지연이 사라진다. **H1은 코드 수준에서 재현·검증됐다.**
단, T6의 전체 TF 시계열·실측이 없으므로 그 회차의 오차 전부가 H1 때문이라고 단정하지 않는다.

### E2. 도착·전진·미션 회귀 검증

`test_shuttle_arrival.py`, `test_shuttle_mission_fsm.py`와 E1을 합해 **40건 통과**.

- Nav2 성공 + 신선한 TF라도 베이 오차 0.39/0.55 m이면 FAILED. AT_BAY·arrived 없음.
- 대기공간 오차 0.55 m이면 WAITING·arrived 없음. 기존 실패 시 토큰 반납 경로는 유지.
- 목표와 좌표가 같더라도 과거 TF·미래 TF·완료 이전 관측만 있으면 제한시간에 포기.
- TF가 없으면 waypoint를 대신 사용해 전진 목표를 보내지 않음.
- 과거 `(-0.60, -0.20)` 대신 새 `(-0.65, -0.02)`와 방향으로 전진 목표를 계산.
- 신선한 0.20 m 도착 오차는 통과. 기존 Nav2 허용오차 정책은 유지.
- 검증 파라미터의 0·음수·NaN·무한대는 주행 목표 전송 전에 거부.
- T_lim을 이미 넘겼거나 완료 폴링 중 넘긴 미션은 늦은 성공을 내지 않음.
- 기존 정상 미션·ArUco 실패·토큰 순서·초기자세 관련 16건도 통과.

재실행 (저장소 루트, ROS 2 Jazzy·기존 mro_interfaces 빌드 필요):

```bash
bash tools/test_shuttle_offline.sh -q -s
```

이 스크립트는 명령 대역을 사용하며 도메인·디스커버리를 실물과 분리한다.
샌드박스에서 UDP 소켓 경고가 있으면 그 결과만으로 통신을 검증했다고 판단하지 않는다.

### E3. 빌드와 정적 검사

- `mro_navigation`, `mro_bringup`: `colcon build --symlink-install` 성공.
- 빌드·설치 경로는 `/tmp/mro-shuttle-tests/` 아래로 분리. 다른 패키지는 기존 install에서 참조.
- Python 문법 검사, 변경 Python 파일의 flake8 E/F/W 검사(W503 제외), 셸 문법 검사 수행.
- `todo_stats.py`로 통계를 갱신했다. `--check`는 기존 9/7 마감의 측위 검증 마커 설치·실측 1건 때문에 exit 1이며 이번 수정의 테스트 실패가 아니다.
- 일반 flake8 전체 설정에는 기존 import/docstring 경고도 있어 전체 lint 무경고로 보고하지 않는다.

## 변경과 결과 피드백

`ShuttleMission`과 `navigator`의 기존 메인 루프는 유지하고, TF 전용
`/<robot>/shuttle_tf` Node와 executor를 분리했다. 종료 시 실행기·스레드·노드를 회수한다.
TF 토픽은 로봇별 `/tf`, `/tf_static` 리맵을 명시하고 `use_sim_time` 초기 설정을 공유한다.

Nav2 SUCCEEDED 후 **완료 이후 시각의 신선한 TF**를 기다리고 XY 오차를 다시 검사한다.
실패하면 다음 단계로 진행하지 않는다. 로그는 ‘실제 위치’ 대신 ‘TF 추정’이라고 표시하고
stamp·지연을 함께 남긴다. 전진도 새로운 TF에서 계산하고 전방 변위를 기록한다.

`common.yaml`의 실험 초깃값은 사용자 승인으로 추가했다. **팀 확정·실물 검증값이 아니다.**

| 파라미터 | 값 | 의미 |
|---|---:|---|
| `tf_pose_timeout_s` | 3.0 s | 새 관측 대기 상한 |
| `tf_max_age_s` | 0.3 s | TF 공통 시각의 최대 지연 |
| `arrival_xy_tolerance_m` | 0.25 m | Nav2 성공 이후 미션 노드의 XY 허용오차 |

이 수정으로 실제 이동거리 0.3 m 또는 cm 단위 정차를 보장하지 않는다.
`bay_advance_m=0.3`은 **신선한 위치에서 계산한 목표 오프셋**이다. Nav2 허용오차와
AMCL의 물리적 오차는 남아 있으므로, 값을 키워 부족분을 덮거나 tolerance를 바로 낮추지 않는다.
I-029의 진동과 H4는 실물 데이터로 별도 확인한다.

기존 I-037의 ‘AMCL로 판정 교체’ 제안은 이번 변경에서 채택하지 않았다.
AMCL 메시지 역시 시각이 오래될 수 있으므로 신선도 검증이 필요하다. 또한 ‘목표 전송 시각의
TF’는 도착 위치가 아닌 과거 위치다. 이번에는 **액션 완료 이후** 관측을 사용한다.

## E4. 실물 재시험 — 사용자 현장 준비 후

1. robot3 도킹·현장 관찰자·비상정지 준비를 확인하고 `shuttle_test_guide.md`의 사전점검을 따른다.
2. `common.yaml`과 `robot3.yaml`을 모두 전달한다. Nav2 tolerance·AMCL 설정·맵은 기준선과 같게 둔다.
3. 미션 전에 별도 TF 기록과 `/robot3/amcl_pose`, `/robot3/navigate_to_pose/_action/feedback` 기록을 시작한다.
   TF·AMCL은 서로 메시지 시각이 다르므로 시간축을 맞춘다. TF stamp만으로 AMCL 관측 나이를 대신하지 않는다.
4. 베이 A 셔틀을 3회 수행하며 `도착 검증 통과/실패`, TF stamp·지연·오차, 전방 변위를 기록한다.
5. 베이에서 base_link의 바닥 투영 위치를 줄자로 측정한다. 범퍼·카메라 등 다른 기준점이면 오프셋을 보정한다.
   5초 체류 중 측정한 값은 도착 직후와 시각이 다를 수 있으므로 측정 시각도 남긴다.
6. 도착 검증 실패 시 미션이 다음 단계로 진행하지 않는지 확인한다. 실물 마커 도착 검증은
   `inject_aruco:=false`와 실제 검출 노드로 별도 수행한다.

소프트웨어 합격: 완료 이후 TF, 지연 ≤ 0.3초, 목표 오차 ≤ 0.25 m, 검증 실패 시
AT_BAY/WAITING/arrived로 진행하지 않음. 물리적 위치 오차와 전진량은 별도로 기록한다.
물리 위치가 목표에서 0.25 m를 넘으면 TF 로그만 통과해도 I-037을 해결로 닫지 않는다.
